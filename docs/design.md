# gamut の設計

gamut は Go のパッケージに機械的な変異を加え、そのパッケージのテストが変異を検出できるかを調べるミューテーションテストツールである。
この文書は、実行の流れ、変異体の表現、schemata の書き換え、判定と報告の形式、採らなかった案を定める。

## 目的

- **速い**：変異体ごとにパッケージをコンパイルし直さない。全変異体を 1 回のビルドに埋め込み、どれを有効にするかを実行時に選ぶ（mutant schemata）。
- **ビルドキャッシュを汚さない**：変異体ごとのビルド結果を共有の Go ビルドキャッシュへ書き込まない。
- **生き残りを仕分けやすくする**：生き残った変異体を、テストが到達しなかったもの、到達したが値が変わらなかったもの、値は変わったが表明が見ていないものに分ける。
- **単純である**：Go の標準ライブラリと `go` コマンドだけに依存する。

## 実行の流れ

1. **読み込み**：引数のパターン（パッケージディレクトリか `<ディレクトリ>/...`）を絶対パスにし、最初のパターンのディレクトリで `go list -json -deps <パターン>...` を実行して対象パッケージのファイルを得て、`go list -export` で依存パッケージのエクスポートデータの場所を得る（「読み込み」）。ビルドタグ（`-tags`）は `go list` と `go test -c` の両方に渡す。対象のファイルは `go list` の `GoFiles` に従い、ビルドの条件を自前で評価しない。対象のファイルを `go/parser` で読み、`go/types` で型を検査する。
2. **列挙**：型情報を使って変異箇所を列挙する。ログ出力の呼び出し（`log`、`log/slog` のパッケージ関数とメソッド）の引数の中は変異しない。生成されたファイル（`// Code generated ... DO NOT EDIT.`）は対象にしない。
3. **構築可能性の判定**：変異体ごとに、演算子の字句だけを置き換えたファイルでパッケージを `go/types` で検査し直す。通らない変異体を `NOT VIABLE` とする。判定は鍵とともにキャッシュに記録し、鍵の変わった変異体だけを CPU の数まで並列に検査する（「変更のない再実行」）。
4. **schemata の書き換え**：構築可能な変異体を埋め込んだソースを一時ディレクトリに作り、書き換え後のパッケージを `go/types` で検査する。エラーを出した箇所は schemata から外し（後述の「個別ビルド」へ回す）、エラーがなくなるまで繰り返す。
5. **ビルド**：パッケージごとに `go test -c -overlay` でテストバイナリを 1 回だけビルドする。元のソースは書き換えない。判定を変えないフラグを足してビルドを短くする（「ビルドのフラグ」）。統合モードでは、逆依存パッケージのテストバイナリも同じ overlay でビルドする（「統合モード」）。
6. **被覆の記録**：`-test.list` でテストの一覧を得て、変異を無効にしたまま、トップレベルのテストをワーカー数の組に分けて組ごとに 1 つのプロセスで実行し、テスト関数の先頭に差し込んだ境目でテストごとに振り分ける（「被覆の記録のまとめ方」）。各テストについて、到達した変異箇所、変異後の値が元の値と異なった変異体、入った関数を記録する。前回の記録を戻せるテストは実行しない（「被覆の記録の再利用」）。ここで失敗するテストがあれば、基準が壊れているので、そのテストの出力を見せて終了コード 4 で中断する。`-test.list` 自体の失敗（`TestMain` の準備の失敗など）も同じに扱う。
7. **自己検査（forced fail）**：到達の記録があるテストのうち最も短い 1 件を、`GAMUT_MUTANT=-1` で 1 回だけ実行し、失敗することを確かめる。キャッシュから記録を戻したテストで検査できるなら、被覆の記録と並行させる。詳しくは「変異の届き方の自己検査」で述べる。
8. **選択**：`-since` か `-mutant` を指定したら、判定する変異体を絞り、残りを `PENDING` にする（「判定する変異体の選択」）。
9. **再利用**：実行が要る変異体のうち、前回の判定の鍵が今と一致するものは、実行せずにキャッシュの判定を使う。詳しくは「判定の再利用」で述べる。
10. **実行**：変異体ごとに、到達したテストだけを、前回の検出テストを先にして順に実行し、最初の失敗で止める（「実行の順序」）。テストプロセスは変異体の間で使い回し、どの変異体を有効にするかを命令で切り替える（「テストプロセスの使い回し」）。`-isolate` では、変異体ごとにプロセスを起動し、`GAMUT_MUTANT` で選び、`-test.run` と `-test.failfast` で絞る。
11. **報告**：判定を JSON に書き、生き残りを分類ごとに標準出力へ並べる。

手順 4 から 7 はパッケージごとに行い、手順 9 と 10 は全パッケージの変異体を 1 つの作業の列にする。詳しくは「複数のパッケージ」で述べる。
無限ループ、`panic`、パッケージ変数の汚染が他の変異体に漏れないよう、落ちたか時間切れになったプロセスと、状態を汚したプロセスは捨てる。
時間切れの上限は、テストのプロセスごとに、そのプロセスで実行するテストの被覆記録時の実行時間の合計に係数を掛け、下限を足して決める。

### 複数のパッケージ

- `go list` の出力のうち、`DepOnly` でなく、テスト以外の Go ファイルを持つパッケージを対象にする。テストファイルしか持たないパッケージは変異の対象がないので外す。補助ファイルのために列挙する標準パッケージも対象にしない。
- 対象のパッケージは同じモジュールに属することを求める。報告の `files[].path` と変異体の識別子はモジュール相対のパスなので、モジュールをまたぐと区別できない。
- 全パッケージで 1 つの `token.FileSet` と、エクスポートデータの importer を共有する。gc の importer は並行に使えないので mutex で守り、読んだ `types.Package` は全パッケージで再利用する。
- 対象パッケージ A が対象パッケージ B を import するとき、A の型検査は B の書き換え前のエクスポートデータを使い、A のテストバイナリは B の書き換え前の版にリンクされる。B の変異は B のテストだけで判定し、A のテストでは検出を試さない。逆依存のテストでの検出は統合モードで扱う。
- schemata の書き換えとビルドとテストの一覧は、パッケージごとにワーカー数まで並列に行う。被覆の記録と変異体の実行は、全パッケージの分を 1 つの作業の列にまとめ、同じワーカーで回す。テストのプロセスの数はパッケージの数によらずワーカー数までになる。
- 変異体の番号（`GAMUT_MUTANT`）はパッケージごとに 1 から振る。テストバイナリはパッケージごとに別なので衝突しない。
- テストファイルを持たないパッケージは、ビルドせずに構築可能な変異体をすべて `NOT COVERED` とする。構築可能な変異体がないパッケージもビルドしない。
- どれかのパッケージで基準のテストか自己検査が失敗したら、どのパッケージも判定せずに止める。一部のパッケージだけの報告は、全体の判定と見分けにくいためである。

### テストバイナリの起動

- テストバイナリの実行（一覧、被覆の記録、自己検査、変異体の実行）にはすべて、利用者のテストのフラグ（`-test-flags`）を先に、gamut が実行ごとに決めるフラグを後に渡す。`-short` のような接頭辞なしの testing のフラグには `-test.` を補い、テストが自分で定義したフラグはそのまま渡す。gamut が決める `run`、`count`、`failfast`、`list`、`paniconexit0` は受け付けない。
- Unix ではテストバイナリを新しいプロセスグループで起動し（`Setpgid`）、時間切れと取り消しではグループ全体へ `SIGKILL` を送る。テストが起動した子プロセスが残って CPU を使い続けたり、出力の管を握って待ちを延ばしたりしないためである。Windows ではテストバイナリだけを止める。止めた後に出力の管が閉じるのを待つ時間は 1 秒までとする（`WaitDelay`）。
- 到達と感染の記録は、変異箇所ごとの `atomic.Bool` と、ファイルへの追記を守る 1 つの mutex で行う。`t.Parallel` のテストや多数のゴルーチンが同じプロセスで変異箇所を通っても記録は欠けない。

### 読み込み

`go list -export -deps` を対象パッケージごと実行すると、編集したばかりの対象パッケージまでコンパイルしてビルドキャッシュに書くが、その結果はどこにも使わない（テストバイナリは書き換えたソースからコンパイルする）。
そこで、依存の一覧（`-export` なし）と、前回の読み込みでエクスポートデータを求めたパッケージ（キャッシュに記録した hint）のエクスポートデータとを並行して求め、足りないものだけを後から求める。

- エクスポートデータを求めるのは、対象パッケージ以外のすべてと、別の対象パッケージが import する対象パッケージである。
- hint が古くても（消えたパッケージを含んでも）、足りないものを求め直すので、型検査の結果は変わらない。
- `-since` の `git diff` と、外の依存の鍵のための `go list -deps -test` も、引数のパターンから求めたモジュールで読み込みと並行して始める。読み込みの結果のモジュールと違えば、捨てて求め直す。

### ビルドのフラグ

テストバイナリのビルドに次のフラグを足す。利用者が `GOFLAGS` で同じフラグを指定していれば足さない。

| フラグ | 効果（idmagic の `usecases` の 1 行の編集後のビルド） | 判定を変えない理由 |
| --- | --- | --- |
| `-vet=off` | 約 20% 短い | `go test -c` が実行する `go vet` の一部の結果は、判定に使わない |
| `-gcflags=<対象パッケージ>=-l` | 約 20% 短い | インライン化の有無はプログラムの意味を変えない。依存のパッケージのフラグは変えないので、依存はビルドキャッシュのものを使う。エクスポートデータに関数の本文が入らないので、本文だけの変更では外部テストのパッケージもコンパイルし直さない |
| `-ldflags=-s -w` | 約 15〜20% 短い | シンボル表とデバッグ情報は、スタックトレースと `runtime.FuncForPC` が使う表（pclntab）と別である |

インライン化を止めると、エスケープ解析の結果が変わり、`testing.AllocsPerRun` で割り当ての数を表明するテストが通らなくなりうる。
その場合は基準のテストの失敗として止まるので、`GOFLAGS=-gcflags=` などで上書きする。

### テストプロセスの使い回し

パッケージの初期化（テストファイルのパッケージ変数を含む）が重いと、変異体ごとにプロセスを起動する時間が実行の大半を占める。
idmagic の `usecases` のテストは、パッケージ変数の初期化で RSA の鍵を 2 つ作り、プロセス 1 つに 0.1〜0.18 秒かかる。
そこで、1 つのテストプロセスで変異体を順に判定する。プロセスは gamut の 1 回の実行の間だけ動く。

- overlay で判定のテスト（`TestGamutServer`、ファイルは `gamut_server_test.go`）を足す。環境変数 `GAMUT_SERVE` があるときだけ働き、ないときは skip する。外部テストのパッケージに置き、内部テストは対象パッケージから公開した関数として呼ぶ。main パッケージは内部テストのパッケージに置き、外部テストもあれば使い回さない。
- 判定のテストは、標準入力から「変異体の番号 テスト名...」の行を受け取り、選択を切り替え（`GamutSetActive`）、テストを `t.Run("g", func(t) { t.Run(name, fn) })` で順に呼ぶ。外側の `t.Run` は並列のサブテストが終わるまで戻らないので、`t.Parallel` のテストも次の変異体へ持ち越さない。
- 結果（「run <名前>」「pass」「fail <名前>」）はファイル記述子 3 に書く。テストの出力と混ざらないためである。
- 変異体を検出したら、検出したテストを変異なしでもう一度実行する。通らなければ、前の変異体か今の変異体がプロセスの状態を汚したので、プロセスを捨て、今の変異体を新しいプロセスで判定し直す。
- プロセスが落ちたら（`panic`、`os.Exit`）、そのとき実行していたテストが検出したとして、プロセスを捨てる。時間切れのプロセスも捨てる。
- 被覆の記録をまとめて測るプロセスも判定のテストで起動し、「cover テスト名...」の命令で測る。測り終えたら記録を止め（`GamutCoverStop`）、そのまま判定に使う。
- 使い回すのはパッケージ自身のテストバイナリだけで、`Test` で始まり `*testing.T` を 1 つ取るテストだけを呼ぶ。`Example`、`Fuzz`、逆依存パッケージのテストを含む変異体は、変異体ごとにプロセスを起動する。
- `-isolate` で、すべての変異体を変異体ごとのプロセスで判定する。

生き残ったときは汚れを確かめない。
汚れは次に検出した変異体の確認で見つかり、その変異体を新しいプロセスで判定し直す。
生き残りの判定が汚れた状態から出た可能性は残るが、汚れはテストを失敗させる向きに働くことが多いので、確認は検出の側に置いた。

### macOS の初回起動の検査

macOS は、新しい実行ファイルが初めて起動されるとき、syspolicyd で XProtect の検査を行う。
idmagic の `usecases` のテストバイナリ（14 MiB）で約 0.35 秒、空のプログラムでも約 0.2 秒かかり、検査の結果はファイルごとに記録される。
コードを変えるたびに新しいテストバイナリができるので、1 回の実行につき 1 回かかる。素の `go test` も同じである。
同じバイナリを同時に複数起動しても、待つのは 1 回分なので、gamut の起動の仕方では減らせない。
システムの設定でターミナルを開発ツールに加えると検査を省けるが、そのターミナルから起動するすべての実行ファイルの検査を止めるので、gamut からは勧めない。

### 時間切れの既定値

既定は係数 5、下限 2 秒である。
2026-11-20 に Apple Silicon の macOS で fixture のテストバイナリを短いテスト 1 件で 300 回起動したところ、起動から終了までは中央値 3 ms、99 パーセンタイル 8 ms、最大 264 ms（最初の 1 回）だった。
並列数を 8 にしても中央値 5 ms、最大 9 ms だった。
短いテストでの揺らぎは下限の 2 秒に比べて十分小さいので、既定値は変えない。
被覆の記録の実行時間は、プロセスの起動と記録の処理を含むので、変異体の実行より長めに出る。上限は安全側に倒れる。

## 判定の再利用

変更のない再実行や、1 関数を変えた後の再実行で、変わらない変異体を実行し直さないため、変異体ごとの判定を鍵とともにキャッシュファイルに保存する。
自己検査は毎回行う。被覆の記録は、前回の記録を戻せるテストを実行しない（「被覆の記録の再利用」）。

- 保存先は `-cache`（既定は作業ディレクトリの `.gamut/cache.json`）で、`-no-cache` で読みも書きもしない。対象のソースツリーへ書き込まないため、モジュールのルートではなく作業ディレクトリを既定にする。
- 主キーは変異体の識別子である。識別子は行と列に依存しないので、位置を補正せずにそのまま引ける。同じ識別子を持つ変異体が 2 体以上あれば（同じ形の `init` が 2 つあるときなど）、それらは再利用しない。
- キャッシュを使うのは、実行が要る変異体（schemata で感染した変異体と個別ビルドの変異体）だけである。`NOT COVERED`、`LIVED`（`not infected`）、型検査による `NOT VIABLE` は、毎回の読み込みと被覆の記録から実行せずに決まる。
- `-mutant` で指定した変異体はキャッシュの判定を使わずに実行し、判定を書き戻す。

### 鍵

どの鍵も、位置とコメントを除いた構文木か、ファイルの中身から作る SHA-256 の先頭 64 ビットである。

| 鍵 | 中身 |
| --- | --- |
| 囲む宣言 | 変異箇所を含む最上位の宣言の構文木。位置、コメント、空白を含めない |
| 依存 | 囲む宣言が `go/types` の参照（`Info.Uses`）で推移的に参照する、同じパッケージの宣言（生成ファイルを含む）の構文木。インターフェースのメソッドの呼び出しは、パッケージの同名のメソッドすべてに届くとみなす。`init` はすべての宣言の依存にする |
| 外の依存 | `go list -deps -test` が返すテストバイナリの依存のうち、メインモジュール（ワークスペースを含む）か版のない replace の先にあるパッケージの Go ファイルと埋め込みファイル、対象パッケージの埋め込みファイル、対象パッケージの `testdata` の下のファイル。パッケージごとに 1 つ |
| テスト | トップレベルのテストの関数と、それが推移的に参照するテストファイルの宣言の構文木。`TestMain` と `init` はすべてのテストに含める。`Example` は期待する出力を書いたコメントも含める |
| 環境 | `go env` の `GOVERSION`、`GOOS`、`GOARCH`、`GOFLAGS`、`GOEXPERIMENT`、`CGO_ENABLED`、`GOWORK`、gamut の実行ファイルの中身、`go.mod`、`go.sum`、`go.work`、変異演算子の集合、ビルドタグ、テストのフラグ、時間切れの係数と下限。ファイル全体に 1 つで、違えば記録をすべて捨てる |

- 依存は宣言の粒度、外の依存はパッケージの粒度にして、粗い側に倒す。
- テストファイルは型検査せず、識別子の名前の一致で参照を近似する。テストだけが import するパッケージのエクスポートデータを読み込みで作っていないためである。同名の局所変数も参照とみなすので、鍵は粗い側に倒れる。
- gamut の版は、開発中の版では文字列が変わらないので、実行ファイルの中身で区別する。

### 再利用の規則

| 状態 | 再利用する条件（どれも、囲む宣言と判定の方式が変わらないことを前提にする） |
| --- | --- |
| `KILLED` | 依存と外の依存が変わらず、検出したトップレベルのテストが変わらず、今回もそのテストを実行する（schemata なら感染する）。検出したテストが分からなければ `LIVED` と同じ規則にする |
| `LIVED`（`not detected`） | 依存と外の依存が変わらず、到達したテストと実行するテストの集合が前回と同じで、そのどのテストも変わらない |
| `TIMED OUT` | 依存と外の依存が変わらない |
| `NOT VIABLE`（個別ビルドでコンパイラが拒んだもの） | 依存と外の依存が変わらない |

被覆の記録は、変わりうるテストを測り直すので（「被覆の記録の再利用」）、到達と感染は今のソースのものとみなせる。
テストの鍵は、テストが呼ぶパッケージの宣言を含めない。
そのため、変異体の宣言が参照せずテストだけが呼ぶ宣言を変え、値は変わるが検出されるかどうかだけが変わる場合は捉えない。
到達と感染が変われば集合の比較で捉える。
`fmt.Stringer` のような、参照の形を取らない呼び出しも依存に入らない。
疑わしいときは `-no-cache` で実行する。

### 書き込み

- 実行が 1 体終わるたびに判定を記録し、終了時に書く。取り消し（`SIGINT`、`SIGTERM`）や基準のテストの失敗で止まったときも、それまでの判定を書く。
- 取り消しの後に終わった実行は記録しない。止められたテストは失敗に見え、`KILLED` と区別できないためである。
- 同じディレクトリの一時ファイルに書いてから改名する。途中で止まっても前のファイルは壊れない。
- 今回判定するパッケージの記録のうち、今回列挙されなかった変異体のものは捨てる。ほかのパッケージの記録は残すので、パッケージを分けて実行しても互いの記録を消さない。1 つのファイルは 1 つのモジュールの記録を持つ（環境の鍵が `go.mod` を含むため）。
- 報告の各変異体には、再利用したかを `cached` に書く。

## 被覆の記録の再利用

被覆の記録は、判定を再利用した後の再実行の時間の大半を占める。
そこで、テストごとの到達、感染、入った関数をキャッシュに保存し、変わりうるテストだけを測り直す。

- 記録は、対象パッケージとテストバイナリのパッケージの組ごとに、トップレベルのテストの名前で引く。
- 変異箇所の番号は書き換えのたびに変わるので、記録には行と列に依存しない鍵を書く。変異箇所は「ファイル、囲む宣言、宣言の中の構文木の経路」のハッシュ（`SiteKey`）、変異体は識別子のハッシュの部分である。
- schemata の書き換えは、対象ファイルの本文を持つ関数の宣言の `{` の直後に、`if gamutCovering { gamutEnter(N) };` を差し込む。同じ行に差し込むので行は変わらない。被覆の記録の実行でだけ働き、テストが入った関数を記録する。`//go:nosplit` の関数には差し込まない（スタックの上限を超えうる）。
- 宣言の到達の鍵（`ReachOf`）は、宣言の構文木と、関数の宣言を経由せずに依存する宣言（定数、型、変数）の構文木のハッシュである。呼ぶ関数は含めない。テストが入った関数はすべて記録されるので、呼ぶ関数の変更はその関数の鍵で捉えられ、含めると呼び出し元に入っただけのテストまで測り直すためである。

次をすべて満たすテストは、記録を戻して実行しない。

| 条件 | 捉える変更 |
| --- | --- |
| 外の依存の鍵が記録と同じ | 手元のモジュールの依存パッケージ、埋め込みファイル、`testdata` |
| 初期化の鍵（パッケージ変数、`init`、生成ファイルの宣言とその依存）が記録と同じ | 初期化で到達する変異箇所はすべてのテストに現れる。生成ファイルの関数には入口の記録を差し込まない |
| 全変異箇所の書き換えの段階（`Wrapped`、`Marked`、`Untouched`）が記録と同じ | 段階が変わると、記録される到達と感染の種類が変わる |
| テストの鍵が記録と同じ | テストの本文と、それが参照するテストファイルの宣言 |
| 記録にある、入った関数と到達した変異箇所を囲む宣言の到達の鍵が、どれも今もある | テストが通った宣言の変更と削除 |
| 記録にある変異箇所と変異体が今もある | ファイルの名前の変更など |

- 新しい宣言には、変わった呼び出し元を経由して入るので、呼び出し元の側で測り直される。
- 同じ鍵の変異箇所が 2 つあれば（同じ形の `init` が 2 つあるときなど）、そのパッケージの記録は戻さない。
- 被覆の記録をすべて戻せ、実行する変異体がなければ、パッケージ自身のテストバイナリもビルドしない。テストの一覧は記録から取り、自己検査も省く。判定はすべて、同じ環境（gamut の実行ファイルを含む）で自己検査を通った実行の記録から来ている。テストの一覧を記録から取るのは、記録のテストの集合がテストファイルのトップレベルのテスト関数の集合と一致し、どのテストの鍵も記録と同じときに限る。
- 戻せない場合として、変わらない呼び出し元から動的な呼び出し（インターフェース）で新しいメソッドに入るようになる変更がある。判定の再利用の `fmt.Stringer` の限界と同じで、疑わしいときは `-no-cache` で実行する。

2026-11-21、idmagic の `backend/oauth2/internal/token/usecases`（563 体、テスト 135 件）で、補助関数 `evaluateForServer` を 1 行変えた後の再実行では、135 件のうちその関数の変異箇所に到達していた 28 件だけを測り直した。

### 被覆の記録のまとめ方

テスト 1 件につき 1 プロセスを起動すると、テストの多いパッケージ（統合モードでは数千件）で被覆の記録が長くなる。
そこで、テストをワーカー数の組に分け、組ごとに 1 つのプロセスで実行する。

- テストファイルを overlay で書き換え、トップレベルのテスト関数の先頭に `GamutTestStart("TestX");` を差し込む。同じ行に差し込むので行は変わらない。`GamutTestStart` は、到達、感染、入った関数の記録を消し、記録のファイルに境目「t <名前>」を書く。外部テストは、対象パッケージを import しているファイルだけ書き換え、公開した関数を呼ぶ。
- テストは `-test.parallel=1` で実行する。`t.Parallel()` を本文の文として呼ぶテストは、その直後にも差し込む。並列のテストは `Parallel` で止まり、ほかのテストの後に再開するので、再開した所を境目にする。本文の中（サブテスト）でも `Parallel` を呼ぶテストは、サブテストの間に別のテストが再開しうるので、まとめずに 1 件ずつ測る。
- 最初の境目より前の記録（パッケージの初期化）は、すべてのテストに足す。
- プロセスが失敗したか、境目のないテストがあれば、その組を 1 件ずつの測定に戻す。基準のテストの失敗は、そこでテストごとに報告する。
- 逆依存パッケージのテストバイナリは、まずテストをまとめて 1 回実行し、変異箇所への到達も関数への入りも記録されなければ、すべて空の記録とする。逆依存パッケージの多くは対象パッケージの変異箇所に到達しないためである。到達があれば 1 件ずつ測る。

## 変更のない再実行

選択のない実行では、入力の指紋と、引数と設定の鍵が前回と同じなら、`go list` も実行せずに前回の報告を返す。

- 指紋は、対象パッケージ（統合モードでは逆依存パッケージも）と外の依存のファイルのディレクトリの直下のファイルの一覧と状態（大きさ、更新時刻、モード）と下位ディレクトリの名前、外の依存のファイルの状態、`testdata` と `<ディレクトリ>/...` の下のすべてのファイルの一覧と状態の SHA-256 である。`go.mod`、`go.sum`、`go.work`、gamut、Go の版は、キャッシュの環境の鍵が捉える。名前が `.` で始まるディレクトリと `node_modules` は、`go` のパターンが見ないので含めない。
- 中身は読まないので、更新時刻を変えずに中身だけを変えた場合は捉えない。疑わしいときは `-no-cache` で実行する。
- 指紋は、テストを実行する前に取る。実行中にファイルが変わっても、変わる前の状態を記録しない。
- 報告は、終了コード 0 で終えた実行のものだけを記録する。

指紋が違えば通常どおり読み込み、構築可能性の判定は鍵の変わった変異体だけを検査する。
構築可能性の鍵は、囲む宣言、依存、外の依存の鍵である。定数宣言の変異体は、型検査がパッケージ全体の定数の値に及ぶので、パッケージ全体の鍵にする。

## 判定する変異体の選択

### 差分（`-since`）

Pull Request の検査やコーディングエージェントの反復で、変えた箇所の検出能力だけを知るための方式である。

- `git merge-base <ref> HEAD` から作業ツリーまでの差分を、`git diff -M --no-prefix -U0` で得る。追跡していないファイル（無視するものを除く）は全体を新しいとみなす。`git` がないか、参照を解決できなければ終了コード 1 で止める。
- 差分は行の単位だが、Go のファイルは変わった行の前後を `go/scanner` で字句に分け、最長共通部分列で突き合わせて、新しい側で変わった字句の区間だけを残す。コメント、空白、改行の位置だけの変更は区間を作らない。消えた字句は、新しい側のその位置に幅 0 の区間を作る。
- 変異体を選ぶのは、変わった区間と、変異箇所の式の区間（`-scope node`、既定）か囲む宣言の区間（`-scope decl`）の交わりである。幅 0 の区間は、区間の内側（端を除く）にあれば交わるとみなす。`decl` は宣言の署名の変更も捉える。
- 差分の外の変異体は `PENDING` とし、数えない。差分に触れないパッケージ（パッケージと逆依存パッケージのディレクトリのファイルが変わらず、差分に交わる変異体もない）はビルドしない。
- 差分の外の変異体のうち、前回 `KILLED` で、検出したテストが今はないものは再検査する。今回検出されなければ、報告に `previously_killed_by` を書き、要約の「no longer detected」に並べる。キャッシュがなければ前回の検出テストが分からないので再検査しない。
- `-include-test-changes` を付けると、差分の外の変異体のうち、前回 `KILLED` でなく、差分が変えたテストが到達するものも再検査する。変えたテストは、テストファイルの宣言のうち変わった区間を持つものを推移的に参照するトップレベルのテストである。`TestMain` か `init` が変わればすべてのテストとする。逆依存パッケージのテストは、テストファイルが変われば、そのパッケージの全テストとする。
- 名前を変えたファイルは `-M` で追い、旧パスでの識別子のキャッシュの判定を新しい識別子へ写す（`IDAt`）。被覆の記録は変異箇所の鍵が変わるので測り直す。
- 被覆の記録は差分によらず「被覆の記録の再利用」の規則に従う。差分の外の変異体の再検査に、今の到達が要るためである。

### 識別子（`-mutant`）

- 識別子か、その一意な前方一致を受け付け、繰り返し指定できる。どれにも当たらないか、複数に当たる指定があれば、候補を並べて終了コード 1 で止める。`-since` とは併用できない（終了コード 2）。
- 指定した変異体を含むパッケージだけを準備する。報告には指定した変異体だけを載せる。
- 被覆の記録は、規則どおり戻せないテストに加えて、指定した変異体の変異箇所に到達していたテストを測り直す。生き残りを埋めるために足したテストは、テストの鍵が変わるので測り直される。
- 指定した変異体はキャッシュの判定を使わずに実行し、判定を書き戻す。

## 実行の順序

### テストの順序

テストは次の順に実行し、最初の失敗で止める。

1. 前回この変異体を検出したテスト。
2. 同じ変異箇所の別の変異体を検出したテスト。キャッシュは実行が終わるたびに書かれるので、今回の実行で先に検出されたものも含む。
3. 残りのテスト。

使い回すテストプロセスでは、判定のテストがこの順に `t.Run` で呼ぶ。
`-isolate` では、1 つのテストのプロセスの中ではテストは `-test.run` の並びによらず宣言の順に走るので、順序はプロセスを分けて決める。
どのプロセスもテストバイナリ 1 つのテストだけを持ち、パッケージ自身のテストバイナリを先にする。
時間切れの上限は、命令かプロセスごとに決める。
前回の検出テストが消えていれば、手順 1 を飛ばす。

### 変異体の順序

変異体の実行は、見積もり時間（実行するテストの被覆記録時の時間の合計。個別ビルドはパッケージのビルド時間を足す）の長い順にする（LPT 規則）。
並列実行の最後に長い変異体が 1 つだけ残って待つことが減る。

2026-11-21、Apple Silicon の macOS、idmagic の `backend/oauth2/internal/token/usecases`（463 体を実行）、ワーカー数 2、`-no-cache` で、変異体の実行の時間を 3 回ずつ測った。

| 順序 | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- |
| 長い順（採用） | 27.0 秒 | 26.7 秒 | 26.4 秒 |
| 短い順 | 27.2 秒 | 28.7 秒 | 27.6 秒 |
| 列挙の順 | 27.0 秒 | 27.5 秒 | 27.5 秒 |

差は数パーセントで、短い順は進行の表示が早く進むほかに利点がなかった。

## 統合モード

Go ではパッケージごとにテストバイナリが分かれるので、呼び出し元のパッケージのテストでしか観測できない振る舞いは、対象パッケージのテストだけでは検出できない。
`-integration` は、逆依存パッケージのテストでも検出を試す。

- 逆依存パッケージは、メインモジュールの全パッケージに `go list -deps -test` を実行し、テストバイナリの依存を逆にたどって求める。テストを持ち、テストバイナリに対象パッケージがリンクされるパッケージである。対象パッケージ自身は含めない。
- 逆依存パッケージのテストバイナリは、対象パッケージの書き換えを渡す同じ overlay でビルドする。変異体の番号は対象パッケージの補助ファイルが持つので、同じ `GAMUT_MUTANT` で選べる。対象パッケージが 2 つ以上あれば、逆依存パッケージのテストバイナリは対象パッケージごとに別にビルドする。1 つのバイナリに 2 つの書き換えを入れると、パッケージごとに 1 から振る番号が衝突するためである。
- 被覆の記録と変異体の実行は、すべてのテストバイナリにまたがって行う。逆依存パッケージのテストの名前は `<import パス>.<テスト名>` にする。パッケージ自身のテストの名前は変えない。
- 逆依存パッケージのテストの鍵はパッケージごとに 1 つで、そのパッケージの Go ファイル、テストファイル、埋め込みファイル、`testdata` と、テストバイナリが依存する手元のパッケージ（対象パッケージを除く）のファイルから作る。
- 被覆の記録をすべて戻せる逆依存パッケージは、テストの一覧を記録から取り、被覆を測るか変異体を実行するまでビルドしない。どのテストも対象パッケージの変異箇所に到達しないパッケージは、その記録がキャッシュに残るので、次からはビルドされない。
- 自己検査はパッケージ自身のテストバイナリだけで行う。
- 個別ビルドの変異体は、パッケージ自身のテストバイナリと、変異箇所に到達したテストを持つ逆依存パッケージのテストバイナリを、その番が来たときに個別にビルドして実行する。到達の記録を持たない変異体（`Untouched`）は、パッケージ自身の全テストと、どれかの変異箇所に到達した逆依存パッケージの全テストで判定する。
- 逆依存パッケージの基準のテストが失敗したときも、判定せずに終了コード 4 で止める。

## 変異演算子

| 名前 | 対象 | 置き換え |
| --- | --- | --- |
| `ARITHMETIC_BASE` | 二項の `+`、`-`、`*`、`/`、`%` | `+`↔`-`、`*`↔`/`、`%`→`*` |
| `CONDITIONALS_BOUNDARY` | `<`、`<=`、`>`、`>=` | `<`↔`<=`、`>`↔`>=` |
| `CONDITIONALS_NEGATION` | `==`、`!=`、`<`、`<=`、`>`、`>=` | `==`↔`!=`、`<`↔`>=`、`>`↔`<=` |
| `INCREMENT_DECREMENT` | `++`、`--` の文 | `++`↔`--` |
| `INVERT_NEGATIVES` | 単項の `-` | `+` |

名前と置き換えは Gremlins と gomutants に合わせる。
どの変異も、演算子の字句 1 つを別の字句に置き換える。
そのため、変異体は「ファイル、字句のバイト位置、元の字句、置き換え後の字句」で表せ、構築可能性の判定と個別ビルドはこの置き換えだけで行える。

## 変異体の識別子

識別子は `<モジュール相対のファイル>::<変異演算子>::<囲む関数>::<ハッシュ>` の形にする。
ハッシュは、囲む関数の名前、関数の中での構文木の経路（子の番号の列）、変異演算子、置き換え後の字句から作る。
行と列を含めないので、関係ない行を追加しても識別子は変わらない。
報告には人が読むための行と列も載せる。

## schemata の書き換え

変異箇所を持つ式を、引数で被演算子を受け取る即時に呼ぶ関数リテラルで包む。

```go
// 元: if a.Count(x) < limit {
if func(l int, r int) bool {
	if gamutCovering {
		gamutHit(4)
		if (l <= r) != (l < r) { gamutInfect(11) }
		if (l >= r) != (l < r) { gamutInfect(12) }
	}
	switch gamutActive {
	case 11:
		return l <= r
	case 12:
		return l >= r
	}
	return l < r
}(a.Count(x), limit) {
```

- 被演算子は引数として 1 回だけ、左から右へ評価する。元の式と同じく、有効にした変異の演算だけを計算する。
- 定数の被演算子と型のない `nil` は、引数にせず本文へそのまま埋め込む。型推論と定数の扱いを元の式と同じにするためである。
- 引数の型は `go/types` の型を、そのファイルの import 名で書く。書けない型（import されていないパッケージの型、別パッケージの非公開の型）を持つ箇所は schemata にしない。
- 入れ子の変異箇所は、内側から書き換えた字句を外側の引数に入れる。被演算子を 1 回しか書かないので、入れ子が深くても字句は増えない。
- `x++` は `func() { if gamutActive == 7 { x-- } else { x++ } }()` という式文に置き換える。`for` の後処理文にも置ける。
- 選択の変数と被覆の記録の関数は、overlay で足す 1 ファイル（`gamut_schemata.go`）に置く。対象パッケージに同じ名前があれば中断する。

書き換え後のパッケージが型検査を通らない箇所（たとえば名前付きの `bool` 型への代入、定数の文脈）は、エラーの位置を含む最も内側の箇所から順に schemata から外す。
外した変異体は、演算子の字句だけを置き換えたファイルを overlay で渡す個別ビルドで判定する。
個別ビルドの変異体は到達の記録を持たないので、全テストを実行する。

### 感染の記録

被覆の記録の実行では、各変異体の変異後の値を計算し、元の値と比べる。
異なれば、その変異体はそのテストで「感染した」と記録する。
変異後の演算が `panic` しうる整数の除算は、除数が 0 なら比べずに感染とみなす。
到達したが一度も感染しなかった変異体は、実行せずに生き残り（理由 `not infected`）と判定する。
この判定は weak mutation の考え方による。値が変わらない以上、どのテストも失敗しえない。

## 変異の届き方の自己検査

schemata の書き換えがテストバイナリに入っていない、または `GAMUT_MUTANT` が子プロセスへ渡っていないと、すべての変異体が `LIVED` か `NOT COVERED` になり、テストの弱さと見分けが付かない。
そこで判定の前に、変異を強制的に失敗させる実行（forced fail）で、変異がテストに届くことを確かめる。

- 補助ファイルの `gamutHit` は、`gamutActive` が `-1`（`schemata.ForcedFail`）なら `panic("gamut: forced fail")` する。各変異箇所の書き換えには字句を足さない。
- `gamutHit` は被覆の記録中にだけ呼ばれるので、検査は `GAMUT_COVER` と `GAMUT_MUTANT=-1` を両方渡して実行する。
- 実行するのは、到達の記録があるテストのうち最も短い 1 件だけである。到達が記録された以上、同じバイナリで `panic` しないなら選択の変数が読まれていない。全テストを実行する必要はない。
- テストが通るか時間切れになったら、判定せずに終了コード 4 で止める。到達のあるテストが 1 件もなければ、検査を飛ばしたことを警告して続ける。
- 個別ビルドの変異体は変異を直接書き込むので、届かない経路がなく、検査しない。
- 対象のコードが `recover` で `panic` を握りつぶすと、選択が届いていても検査が失敗しうる。その場合のエラーメッセージはこの可能性も挙げる。

## 判定と報告

| 状態 | 意味 |
| --- | --- |
| `KILLED` | 選んだテストのどれかが失敗した |
| `LIVED` | 生き残った。`reason` が `not infected`（到達したが値が変わらない）か `not detected`（値は変わったが失敗しない） |
| `NOT COVERED` | どのテストも到達しなかった |
| `NOT VIABLE` | 変異後のパッケージが型検査を通らない |
| `TIMED OUT` | 時間切れの上限を超えた |
| `PENDING` | 選択（`-since`）の外にあり、判定しなかった。数えない |

JSON の報告は gomutants と同じ `files[].mutations[]` の形にし、各要素に `id`、`type`、`status`、`line`、`column`、`original`、`replacement` を持たせる。
gamut は加えて `reason`、`tests`（到達したテスト）、`killed_by`、`mode`（`schemata` か `standalone`）、`cached`（判定をキャッシュから再利用したか）、`previously_killed_by`（前回の検出テストが消えて検出されなくなったときの、そのテスト）を持たせる。
最上位には `mutants_pending`（`PENDING` の数）を足す。`mutants_total` と効率の計算は `PENDING` を含めない。
`files[].path` はモジュール相対のパスである。
最上位の `package` は、1 パッケージならその import パス、複数なら引数に指定したパターンを空白でつないだものにし、判定したパッケージの import パスを `packages` に並べる。
gomutants の報告を読む既存の検査は、そのまま gamut の報告を読める。

終了コードは、0 が判定を終えたこと、1 が読み込みやビルドなどの誤り、2 が引数の誤り、4 が基準のテストの失敗か自己検査の失敗で判定しなかったことを表す。

### Go ならではの強み

Go の性質を使う方向を挙げる。

- **型による確実な構築可能性**：`go/types` は Go のコンパイラと同じ規則で検査するので、構築不能の判定に漏れがほぼない。
- **静的な被覆の補助**：Go の呼び出しは静的に解決しやすいので、`golang.org/x/tools` を使わずとも、`go/types` の参照から変更の影響を受けるテストを絞れる。
- **テストバイナリが単一の実行ファイルである**：判定のテストを overlay で足すだけで、1 つのプロセスの中で変異体を切り替えられる。プロセスを捨てて起動し直すのも容易なので、汚れたときだけ隔離に戻せる。

## 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 変異体ごとに overlay でビルドする | 変異体の数だけコンパイルとリンクを繰り返し、結果が共有のビルドキャッシュにたまる。この方式では idmagic の 563 体のパッケージで 352 秒、2.6 GiB だった |
| 元の値と変異後の値を両方計算する選択関数（`sel(id, a+b, a-b)`）で包む | 副作用のある被演算子を 2 回評価し、元のプログラムにない `panic`（0 除算）を起こす |
| 被演算子を関数リテラルの本文に 2 回書く | 入れ子の変異箇所で字句が指数的に増える |
| 変異体ごとにプロセスを分ける（`-isolate` として残す） | パッケージの初期化が重いと、起動の時間が実行の大半を占める。idmagic の `usecases` の初回で、使い回す方式の 6.5 秒に対して 36.5 秒だった。状態の漏れは汚れの確認で捉える |
| 生き残った変異体の後にも汚れを確かめる | 変異体ごとに検出したテストを実行し直すので、生き残りの多いパッケージで実行が倍近くになる。汚れは次の検出の確認で見つかる |
| 被覆の記録の境目を `-test.v` の出力の `=== RUN` と `=== CONT` から取る | 記録はファイルに、出力は標準出力に書かれるので、両者の前後関係が分からない |
| インライン化をすべてのパッケージで止める（`-gcflags=all=-l`） | 依存のパッケージがすべてビルドキャッシュに当たらなくなり、初回が遅く、キャッシュも増える |
| 最適化も止める（`-gcflags=<対象>=-N -l`） | ビルドはインライン化の停止だけと変わらず、テストが遅くなる |
| macOS で開発ツールの設定を勧める | 初回起動の検査（約 0.35 秒）は消えるが、そのターミナルから起動するすべての実行ファイルの検査を止める |
| `golang.org/x/tools/go/packages` で読み込む | 依存が増える。`go list -export` とエクスポートデータの importer で足りる |
| パッケージ単位で判定をキャッシュする | import 先の変更を追えず、古い判定を返しうる。1 関数の変更でパッケージの全変異体を実行し直す |
| 判定と一緒に元のソースを保存し、差分で位置を補正する | 報告が肥大し、依存の変更を捉えない。識別子が位置に依存しないので補正は要らない |
| 被覆の記録の再利用で、テストが名前で参照する宣言から到達を静的に推定する | 同名の局所変数や、呼ばない宣言の参照で測り直しが増える。外のパッケージ（`sort.Sort` など）から呼ばれる宣言を捉えない。入った関数の記録は、被覆の記録の実行でだけ働き、正確である |
| `-test.run` の並びでテストの順序を決める | テストは 1 つのプロセスの中では宣言の順に走るので、並びは順序を変えない |
| 統合モードで、逆依存パッケージのテストバイナリに対象パッケージすべての書き換えを入れる | 変異体の番号はパッケージごとに 1 から振るので、1 つの `GAMUT_MUTANT` が複数のパッケージの変異体を有効にする |
| テストの鍵に、テストが呼ぶパッケージの宣言を含める | 1 関数を変えると、それを呼ぶテストが到達する別の宣言の変異体まで実行し直す。到達と感染の変化は毎回の被覆の記録で捉えられる |
